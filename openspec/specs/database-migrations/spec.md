## ADDED Requirements

### Requirement: Alembic configuration
The system SHALL provide an Alembic setup under `backend/alembic/` that introspects ORM metadata and generates migrations from model changes.

#### Scenario: alembic.ini lives at backend root and points to backend/alembic
- **WHEN** the repository is cloned
- **THEN** `backend/alembic.ini` exists with `script_location = alembic`, `sqlalchemy.url` pulled from `DATABASE_URL` env var via `env.py`, and `file_template` configured for sortable migration filenames

#### Scenario: env.py exposes Base.metadata as target_metadata
- **WHEN** Alembic starts
- **THEN** `backend/alembic/env.py` imports `Base` from `backend.shared.database`, sets `target_metadata = Base.metadata`, configures `compare_type=True` and `compare_server_default=True` in `context.configure(...)`

#### Scenario: env.py imports all models so autogenerate sees them
- **WHEN** `alembic revision --autogenerate` runs
- **THEN** `env.py` (or a sibling module imported by it) has imported every model module under `backend/features/*/models.py` so SQLAlchemy registers all tables in `Base.metadata`

### Requirement: Initial monolithic migration
The system SHALL ship a single initial migration that creates the entire schema from an empty database.

#### Scenario: Migration is autogenerated from current models
- **WHEN** the developer runs `alembic revision --autogenerate -m "0001_initial_schema"` against an empty database
- **THEN** Alembic produces one migration file under `backend/alembic/versions/` containing `op.create_table(...)` for all 16 entities (`users`, `roles`, `user_roles`, `refresh_tokens`, `delivery_addresses`, `categories`, `ingredients`, `products`, `product_categories`, `product_ingredients`, `payment_methods`, `order_states`, `orders`, `order_items`, `payments`, `order_state_history`)

#### Scenario: Migration includes ARRAY(Integer) for personalizacion
- **WHEN** the initial migration is reviewed
- **THEN** the `order_items.personalizacion` column is created with `sa.ARRAY(sa.Integer())` (manually added if autogenerate omits it)

#### Scenario: Migration includes CHECK constraints
- **WHEN** the initial migration is reviewed
- **THEN** it includes `CHECK (precio > 0)` on `products.precio`, `CHECK (stock_cantidad >= 0)` on `products.stock_cantidad`, and `CHECK (cantidad > 0)` on `order_items.cantidad` (manually added if autogenerate omits them)

#### Scenario: Migration applies to empty database without errors
- **WHEN** `alembic upgrade head` runs against an empty PostgreSQL database
- **THEN** all 16 tables exist, all FKs resolve, and `alembic_version` table records the revision id

#### Scenario: Auto-upgrade on app startup is NOT performed
- **WHEN** the FastAPI application starts
- **THEN** it does NOT execute `alembic upgrade head` automatically; migrations run via explicit CLI invocation or CI

### Requirement: Idempotent seed script
The system SHALL provide a seed script `backend/scripts/seed.py` invocable as `python -m backend.scripts.seed` that loads minimal canonical data idempotently.

#### Scenario: Seed loads catalogs and admin user
- **WHEN** the seed runs against a freshly migrated empty database
- **THEN** it inserts 4 rows in `roles` (IDs 1..4 with codes ADMIN/STOCK/PEDIDOS/CLIENT), 6 rows in `order_states`, 3 rows in `payment_methods`, 1 row in `users` for admin, 1 row in `user_roles` linking admin to role ADMIN

#### Scenario: Seed uses ON CONFLICT DO NOTHING
- **WHEN** the seed runs a second time against the same database
- **THEN** every INSERT uses `pg_insert(...).on_conflict_do_nothing()` (PostgreSQL dialect) and completes without raising integrity errors and without creating duplicate rows

#### Scenario: Seed reads admin password from environment
- **WHEN** the seed runs with `ADMIN_PASSWORD=mysecret` in env
- **THEN** the admin user is created with bcrypt hash of `'mysecret'`

#### Scenario: Seed warns on default password
- **WHEN** the seed runs without `ADMIN_PASSWORD` in env
- **THEN** a WARNING-level log line is emitted to stderr indicating the insecure default `admin1234` is being used, and the admin is still created with that hash

#### Scenario: Seed exits with non-zero on database connection failure
- **WHEN** the seed runs but cannot connect to the database
- **THEN** it logs an error and exits with non-zero status

### Requirement: Migration moves es_removible from pivot to Ingrediente
The system SHALL provide an Alembic migration that: (1) adds `es_removible BOOLEAN NOT NULL DEFAULT false` to the `ingredients` table, (2) drops the `es_removible` column from the `product_ingredients` table. The migration SHALL log the count of affected rows before dropping the pivot column. `down_revision` SHALL point to the latest existing migration.

#### Scenario: Upgrade adds column to ingredients and drops from product_ingredients
- **WHEN** `alembic upgrade head` is executed
- **THEN** the `ingredients` table has `es_removible BOOLEAN NOT NULL DEFAULT false` AND the `product_ingredients` table no longer has `es_removible`

#### Scenario: Existing ingredients get default false
- **GIVEN** the `ingredients` table has rows before migration
- **WHEN** `alembic upgrade head` is executed
- **THEN** those rows have `es_removible = false`

#### Scenario: Downgrade reverses the operation
- **WHEN** `alembic downgrade -1` is executed
- **THEN** `es_removible` is removed from `ingredients` AND re-added to `product_ingredients` with `DEFAULT false`

#### Scenario: Migration logs affected pivot rows
- **WHEN** the upgrade runs
- **THEN** a log message reports how many `product_ingredients` rows had `es_removible = true` before the column is dropped

### Requirement: Naming conventions for migration metadata
The system SHALL configure SQLAlchemy `MetaData` with a deterministic naming convention so Alembic generates stable constraint names.

#### Scenario: Naming convention is set on MetaData
- **WHEN** `Base.metadata` is initialized
- **THEN** it uses `naming_convention={"ix": "ix_%(column_0_label)s", "uq": "uq_%(table_name)s_%(column_0_name)s", "ck": "ck_%(table_name)s_%(constraint_name)s", "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s", "pk": "pk_%(table_name)s"}` so autogenerated migrations get reproducible constraint names across runs

### Requirement: Environment configuration
The system SHALL document required environment variables for migration and seed in `.env.example`.

#### Scenario: .env.example documents migration/seed variables
- **WHEN** a developer reads `.env.example`
- **THEN** it lists `DATABASE_URL` (with example format `postgresql+psycopg://user:pass@localhost:5432/foodstore_dev`) and `ADMIN_PASSWORD` (commented with note "leave empty for insecure default 'admin1234' in dev")

### Requirement: Smoke test command sequence
The system SHALL document and support a manual smoke test that proves the schema and seed work end-to-end on an empty database.

#### Scenario: Documented smoke test runs cleanly
- **WHEN** a developer follows the README/AGENTS.md smoke test (drop dev DB → create empty DB → `alembic upgrade head` from `backend/` → `python -m backend.scripts.seed`)
- **THEN** the dev database ends with all 16 tables created, the catalogs and admin user populated, and the script exits with status 0
